# Day 4 validation · 28 October 2026

This note records the local Day 4 evidence with the paid Cavioo host attempt and its retained-record follow-up. The work uses the fresh public engine and its separate local proof host. Cavioo's existing components and layout remain the integration target.

## Impact on the system

An ordinary return check can now preserve its complete original evidence while sending three screenshots to the analyst. For example, the robot enters the approved synthetic email, visits review, returns, and compares the original entry with the returned field. The four original screen records are before typing, after typing, before Back and after Back. All four records, their original hashes and source links remain available. All four original image files still have their bytes checked.

Only the pre-typing picture can be records-only: its original record is read, but its screenshot is not attached. The analyst receives the other three original screenshots under their own original screen IDs. The engine applies this exception only to one complete, intact approved return chain: the actual approved type action, observed field identity, original entry baseline, actual Back action, chronological order and completed comparison must agree. Missing fields, a different typed value, missing sources or an unperformed comparison cannot earn the exception. An independently required visual or measurement source prevents it. Pictures are neither combined nor relabelled, and byte-equivalent pictures are not assumed.

Each new request saves an **image receipt**: an explicit list of the original screenshots supplied and any strictly permitted records-only baseline. Its version is `original-images/1`. The receipt identifies each original screen record, its record hash and its image hash. The request adapter checks the stored read, the exact image list and the actual attached bytes before sending a request. Legacy reads without a receipt retain their previous all-selected-images meaning; they receive no implicit baseline exemption.

New findings, criterion proposals, visual observations, visual coverage and reviews also save the hash of the read they used. That hash covers the receipt and original-record list. Changing a read and recomputing its own hash cannot change which images supported an existing result. Removing a new receipt cannot make a stored read-hash requirement disappear. These checks apply during creation and again when findings, criteria and visual coverage are read for delivery.

The assessed criterion screen and every visual or element target must have an actually supplied image. A records-only baseline cannot receive a visual examination, become a finding target, or gain an assessed criterion result. The reviewer receives all required original images independently, within its existing eight-image allowance. A `keep` response cannot supply an image the analyst never received or repair missing evidence. The analyst's three-image limit, driver's one-image limit, existing request/token limits, browser-action limit and $3 run ceiling remain unchanged. No additional reasoning role or automatic paid retry is introduced.

The analyst now receives the latest review for each exact finding version, plus the most recent adverse review when it is a different record. For example, an earlier request to remove an unsupported keyboard claim remains visible even if a later review kept the finding. This feedback is an interpretation to reconsider against the original walk, navigator notes, measurements and screenshots. It adds no pictures and does not expand old review reads. Review records, earlier candidates, read manifests, model responses and coverage interpretations cannot become factual finding sources. A visual observation is permitted only through its existing exact image, topic and visible-premise checks. A corrected finding remains a distinct version requiring a fresh exact review.

Final delivery independently checks that the review used an actual reviewer read. For new findings, a kept review cannot silently replace the candidate's title. Every original dependency must match the candidate's pinned analyst read, including its original source links and order; a fact learned only during later review cannot repair the earlier claim. Engine-created visual interpretation records can follow their read, but their original dependencies must match their own pinned analyst read as well. Intended historical saved reviews and no-issue-key title behavior remain compatible. Direct retained-record regressions and deliberate guard removals verify these rules independently of the normal model-response binder.

The separate local host can explicitly opt into controlled inference through `--controlled-live-proof`. Its default remains offline. The opt-in requires a key and a current approval capped at $3 total and per run, uses the existing authenticated host connection, fixes the configured mode and prevents an arbitrary target URL. The ordinary frontend cannot enable it. Repeated start requests reuse the same run; controlled inference has no manual Advance step. These are local controlled-test controls; the actual run and limits are recorded below.

## Impact on the UX

Cavioo's layout and components are unchanged by the public-engine work. The intended flow remains the website browser, reviewed live finding bubbles, then the report and original screenshots. A missing picture or unsupported return comparison stays unknown instead of becoming an apparent pass or an invented finding.

For example, the approved synthetic email surviving Back can support a reviewed, scoped return result. Its pre-typing screenshot cannot simultaneously support a visual criticism when it was not supplied to the analyst. A later corrected finding must receive its own exact review before delivery.
